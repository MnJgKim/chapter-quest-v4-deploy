# 자동 공개 예약 설계 검토 — 운영 적용 금지

## 확인된 운영 동작
`cq_v4_is_released`는 학생별 배정 행의 `released_at IS NOT NULL` 및
서울 현지 날짜 `>= lesson_date`를 **모두** 요구한다.
기존 `cq_v4_parent_set_lesson_release`는 부모가 공개 버튼을 눌러야
`released_at`을 기록한다. 따라서 단순히 배정 날짜를 추가하는 것만으로
요일별 자동 공개는 작동하지 않는다.

## 권장 설계: 사전 공개 승인(arm) + 날짜 게이트
부모가 자동 배정 정책을 승인한 경우에 한하여, 승인된 챕터를 해당
학습일에 배정하는 **동일 트랜잭션** 안에서 `released_at=now()`로 기록한다.
학생 접근은 기존 `cq_v4_is_released`의 서울 날짜 게이트에 의해
학습일 이전까지 차단된다. 매일 새벽 Cron으로 공개 플래그를
갱신할 필요가 없다.

기본 `cq_v4_parent_schedule_week_atomic`은 계속
`released_at=NULL`로 삽입한다. 사전 공개 승인은 별도 명시적 인자와
서버 검증으로만 처리해야 하며, 임의 클라이언트가 공개를 활성화하는
API를 만들면 안 된다.

## 필수 보안/동작 조건
1. `auth.uid()`가 학생의 부모 관리자이며 등록 관계가 유지돼야 한다.
2. 원본 PDF 준비/검증, 학생 배정, 최종 게시된 활동과 승인 해시가
   모두 DB에서 재검증돼야 한다.
3. 학생별 요일 정책: 서우 월/수/목, 서진 화/수/금,
   시우 월~금(임시값); 관리자가 변경할 수 있도록 한다.
4. 기존 수동 배정, 이미 제출한 챕터, 동일 날짜 배정을 덮어쓰지 않는다.
5. 부모가 공개를 취소한 행은 후속 자동 배정 작업에서 다시
   공개하지 않는다. 별도의 취소 기록/정책 상태가 필요하다.
6. 미래 학습일은 서울 시간 기준으로 날짜를 판정한다.
7. 부모의 자동 공개 동의 및 실행 이력을 남기고, 학생별 중단 기능을 둔다.
8. 반복 실행은 멱등성을 보장하고, 서로 다른 스케줄 작성 경로의
   동시성은 학생/날짜 고유 제약으로 보호한다.
9. `released_at` 사전 기록의 의미(실제 공개 시각이 아님)를
   UI/감사 로그에서 명확히 구분한다.

## 배포 전 검증
- 미래 날짜 예약: 날짜 이전 비공개 / 당일 자동 공개
- 학습일 경계: Asia/Seoul 자정 전후
- 공개 취소: 다음 실행에도 비공개 유지
- 승인 취소/내용 변경 후 재공개 금지
- 수동 일정 유지 및 동시 실행 충돌
- 실기기 모바일/갤럭시 태블릿 검증
- 전체 Supabase 데이터 및 Auth/Storage 백업, Cloudflare 롤백 검증
- 사용자 운영 배포 승인

이 문서는 구현 설계이며, 아직 자동 공개 RPC·UI·스케줄러가 구현되거나
운영 배포된 상태가 아니다.
