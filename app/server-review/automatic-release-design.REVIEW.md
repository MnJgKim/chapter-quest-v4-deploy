# 자동 공개 예약 설계 검토 — 운영 적용 금지

## 확인된 운영 동작
`cq_v4_is_released`는 학생별 배정 행의 `released_at IS NOT NULL` 및
서울 현지 날짜 `>= lesson_date`를 **모두** 요구한다.
기존 `cq_v4_parent_set_lesson_release`는 부모가 공개 버튼을 눌러야
`released_at`을 기록한다. 따라서 단순히 배정 날짜를 추가하는 것만으로
요일별 자동 공개는 작동하지 않는다.

## 권장 설계: 사전 공개 승인(arm) + 날짜 게이트
부모가 자동 배정 정책을 승인한 경우에 한하여, 승인된 챕터를 해당
학습일에 배정하는 **동일 트랜잭션** 안에서 `released_at=now()`로 기록한다.
학생 접근은 기존 `cq_v4_is_released`의 서울 날짜 게이트에 의해
학습일 이전까지 차단된다. 매일 새벽 Cron으로 공개 플래그를
갱신할 필요가 없다.

기본 `cq_v4_parent_schedule_week_atomic`은 계속
`released_at=NULL`로 삽입한다. 사전 공개 승인은 별도 명시적 인자와
서버 검증으로만 처리해야 하며, 임의 클라이언트가 공개를 활성화하는
API를 만들면 안 된다.

## 필수 보안/동작 조건
1. `auth.uid()`가 학생의 부모 관리자이며 등록 관계가 유지돼야 한다.
2. 원본 PDF 준비/검증, 학생 배정, 최종 게시된 활동과 승인 해시가
   모두 DB에서 재검증돼야 한다.
3. 학생별 요일 정책: 서우 월/수/목, 서진 화/수/금,
   시우 월~금(임시값); 관리자가 변경할 수 있도록 한다.
4. 기존 수동 배정, 이미 제출한 챕터, 동일 날짜 배정을 덮어쓰지 않는다.
5. 부모가 공개를 취소한 행은 후속 자동 배정 작업에서 다시
   공개하지 않는다. 별도의 취소 기록/정책 상태가 필요하다.
6. 미래 학습일은 서울 시간 기준으로 날짜를 판정한다.
7. 부모의 자동 공개 동의 및 실행 이력을 남기고, 학생별 중단 기능을 둔다.
8. 반복 실행은 멱등성을 보장하고, 서로 다른 스케줄 작성 경로의
   동시성은 학생/날짜 고유 제약으로 보호한다.
9. `released_at` 사전 기록의 의미(실제 공개 시각이 아님)를
   UI/감사 로그에서 명확히 구분한다.

## 배포 전 검증
- 미래 날짜 예약: 날짜 이전 비공개 / 당일 자동 공개
- 학습일 경계: Asia/Seoul 자정 전후
- 공개 취소: 다음 실행에도 비공개 유지
- 승인 취소/내용 변경 후 재공개 금지
- 수동 일정 유지 및 동시 실행 충돌
- 실기기 모바일/갤럭시 태블릿 검증
- 전체 Supabase 데이터 및 Auth/Storage 백업, Cloudflare 롤백 검증
- 사용자 운영 배포 승인

## 2026-11-17 개발 브랜치 구현 및 운영 호환성 확인
- 개발 브랜치에 자동 공개 정책·취소·예약 RPC, 부모 UI, PGlite 테스트가 구현되어 있다. **운영에는 아직 미적용**이다.
- 운영 `cq_v4_lesson_schedule`에는 `parent_user_id`가 존재하며, 소유권 확인 및 insert에 필수이다.
- 운영 `cq_v4_parent_set_lesson_release(uuid,uuid,boolean)`의 반환형은 `void`이고, 관리자·소유권·게시 상태를 검사한다. 개발 브랜치의 수동 오버라이드 RPC가 이 시그니처를 호출한다.
- 운영 `cq_v4_is_released(uuid,uuid)`는 `released_at`과 학습일 현지 날짜 게이트를 모두 확인한다. Cron 없는 사전 승인 설계와 호환된다.
- 운영 읽기 전용 점검에서 PDF 미검증, 미게시 활동, 일정 배정 누락, 일정 게시 활동 누락, 학생/날짜 중복이 모두 0건이었다.
- 자동화 일정 안전성 테스트는 통과했지만 전체 백업·복구 검증과 실제 기기 E2E는 아직 완료되지 않았다.

## 적용 차단 조건
운영 DB/Auth/Storage 전체 백업과 Cloudflare 현재 설정/버전 보존 및 복구 절차를 확보하고, 사용자에게 변경 사항·위험·롤백 계획을 제시하여 **명시적 승인**을 받은 후에만 운영 변경을 수행한다.


## 신규 발견: 기존 게시 자료와 신규 승인 증빙 간 불일치
- 운영 **읽기 전용** 검증: 예약된 11건 모두 게시된 활동과 배정이 있지만, 11건 모두 신규 자동 예약 RPC가 요구하는 **엄격한 승인 증빙(64자리 해시 + 승인 요청 일치)** 조건을 충족하지 않는다.
- 이 중 10건은 `cq_v4_activities.approval_id` 및 `approval_hash`가 비어 있고, 나머지 1건은 승인 요청 연결은 있으나 해시 형식이 64자리 소문자 16진수 규칙에 맞지 않는다.
- 따라서 현재 게시된 자료를 새 자동 예약 RPC로 다시 예약하는 시도는 실패할 수 있다. 기존 수동 예약이나 학생 접근 정책을 임의로 변경해서 해결하지 않는다.
- 해결 방향: 기존 자료의 출처·승인 이력을 검증하여 실제로 승인된 자료만 신규 정책으로 **명시적 재승인** 처리하거나, 별도의 검증 가능한 레거시 승인 경로를 설계한다. 허위 해시 생성이나 승인 검증 완화 금지.
- 이미 배정된 기존 학습일은 신규 자동 예약으로 덮어쓰지 않는다. 기존 예약은 유지하고 향후 미배정 학습일에 대한 승인된 자료부터 자동 예약한다.
- 이 문제는 **운영 적용 전 해결해야 하는 차단 조건**이다.
